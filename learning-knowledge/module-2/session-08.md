# Сессия 8 — Методичное использование ИИ: правила проекта, skills и агенты

> Модуль 2, Неделя 4 | Видео перед сессией рекомендуется
> **Артефакт** : проект с настроенными AI-инструкциями, одним переиспользуемым skill и одним примером агента / agent mission для ревью спеки

---

## Философия С8

**С8 переводит студента от "я пишу промпт" к "я настраиваю рабочую систему для ИИ".**

До этого момента студенты уже увидели :

1. что проект может жить как настоящее Next.js-приложение
2. что проект можно запускать локально через `localhost`
3. что Git дает проекту историю
4. что GitHub и Vercel дают проекту удаленную жизнь и онлайн-URL
5. что файл инструкций вроде `AGENTS.md`, `CLAUDE.md` или `GEMINI.md` помогает ИИ лучше понимать проект

Теперь нужно сделать следующий шаг.

На С7 мы сказали :

> "Файл инструкций — это память проекта для ИИ."

На С8 мы добавляем :

> "Но одной памяти недостаточно. Для серьезной работы нужен метод."

### Главная проблема, которую нужно поставить

Многие используют ИИ так :

- открывают чат
- пишут один большой промпт
- получают результат
- потом пишут новый промпт
- потом снова объясняют проект
- потом снова исправляют то, что ИИ не понял

Это работает для маленьких задач.

Но как только появляется настоящий проект, начинаются проблемы :

- ИИ забывает правила
- ИИ предлагает не тот стек
- ИИ меняет слишком много файлов
- ИИ делает "красиво", но не по задаче
- ИИ начинает кодить до того, как понял контекст
- студент не понимает, где закончилась его роль и где началась роль агента

**Центральная идея С8** :

> Сильная работа с ИИ — это не один идеальный промпт. Это система : правила, skills, агенты и проверка.

### Главный ментальный переход

До С8 :

```text
Я прошу ИИ что-то сделать.
```

После С8 :

```text
Я настраиваю условия, в которых ИИ работает правильно чаще.
```

То есть студент должен начать думать не только о формулировке запроса, но и о среде :

- что ИИ должен знать всегда
- какую процедуру ИИ должен повторять
- какую роль можно делегировать отдельному агенту
- как проверить, что ИИ действительно увидел инструкции

### Четыре слоя методичной работы с ИИ

Для новичков лучше всего дать простую лестницу :

1. **Prompt** — разовая просьба
2. **Rules / memory** — постоянные правила проекта
3. **Skill** — повторяемая процедура
4. **Agent** — специализированная роль с миссией

Формула :

> Prompt отвечает на вопрос "что сделать сейчас". Rules отвечают "как работать в этом проекте". Skill отвечает "как выполнять эту процедуру". Agent отвечает "кому делегировать эту роль".

### Чего нельзя допустить педагогически

После С8 студент не должен уйти с такими ложными выводами :

- "skill — это просто длинный промпт"
- "agent — это магический сотрудник, которому можно доверить все"
- "если я создал `AGENTS.md`, ИИ обязан на 100% слушаться"
- "нужно сразу настроить все инструменты"
- "чем больше правил, тем лучше"

Правильная картина :

- правила дают стабильный контекст
- skills дают повторяемые процедуры
- агенты помогают делегировать узкие роли
- все это улучшает качество, но не отменяет проверку человеком
- начинать нужно с малого : один файл правил, один skill, один агент

### Скрытая цель С8

Сделать так, чтобы студент перестал видеть ИИ как "чат, который иногда помогает".

После этой сессии ИИ должен начать восприниматься как :

- рабочая система
- с правилами
- с повторяемыми процедурами
- с ролями
- с контролем результата

## ВСТУПЛЕНИЕ — Почему одного промпта уже недостаточно (10 мин)

### 1.1 — Начать с знакомой ситуации

Можно начать так :

> "Вы уже умеете просить ИИ создать страницу, исправить ошибку, объяснить код или помочь с проектом. Это уже сильный навык. Но сегодня мы увидим его предел."

Потом нарисовать типичный хаос :

```text
Промпт 1: сделай страницу
Промпт 2: нет, используй Next.js
Промпт 3: нет, не меняй дизайн
Промпт 4: нет, у нас TypeScript
Промпт 5: нет, не трогай эту папку
Промпт 6: почему ты снова забыл?
```

Сказать :

> "Когда вы каждый раз повторяете одно и то же в промпте, это значит, что это уже не промпт. Это правило проекта, которое нужно вынести в файл."

### 1.2 — Проблема разовых запросов

Разовый prompt хорош, когда задача маленькая :

- "объясни этот код"
- "переименуй кнопку"
- "сделай текст короче"

Но он слабее, когда задача повторяется :

- "каждый раз проверяй спецификацию"
- "каждый раз не трогай `.env`"
- "каждый раз запускай тесты"
- "каждый раз сравнивай код с задачей"

Если просьба повторяется, ее нужно превратить в структуру :

- правило
- skill
- агент

### 1.3 — Ключевая фраза

> "Prompt — это не система. Prompt — это только вход в систему."

### 1.4 — Связка с С7

На С7 мы дали проекту память :

- Git помнит изменения
- GitHub хранит историю онлайн
- Vercel публикует версию
- файлы инструкций дают ИИ контекст

На С8 мы говорим :

> "Теперь мы не просто даем ИИ память. Мы даем ему метод работы."

## ЧАСТЬ 1 — Карта метода : prompt, rules, skill, agent, verification (14 мин)

### 2.1 — Простая лестница

Нужно нарисовать на экране :

```text
Prompt
  -> Rules
  -> Skill
  -> Agent
  -> Verification
```

И пройти очень просто.

### 2.2 — Prompt

**Prompt** — это разовая просьба.

Пример :

```text
Добавь на главную страницу блок с тремя преимуществами моего сервиса.
```

Prompt отвечает на вопрос :

> Что нужно сделать сейчас ?

### 2.3 — Rules / memory

**Rules** — это постоянные правила проекта.

Пример :

```md
- Проект использует Next.js App Router.
- Не менять `.env`.
- Все тексты интерфейса писать на русском.
- Перед финальным ответом проверять `npm run build`.
```

Rules отвечают на вопрос :

> Как нужно работать в этом проекте почти всегда ?

### 2.4 — Skill

**Skill** — это повторяемая процедура.

Пример :

```text
Когда я прошу проверить spec, сделай 5 шагов:
1. прочитай spec
2. найди обещанные функции
3. проверь код
4. составь список расхождений
5. предложи следующий шаг
```

Skill отвечает на вопрос :

> Как выполнять эту повторяемую работу ?

### 2.5 — Agent

**Agent** — это специализированная роль.

Пример :

```text
Ты spec-reviewer. Твоя задача — проверять соответствие проекта spec. Ты не кодишь, ты только находишь расхождения.
```

Agent отвечает на вопрос :

> Какую роль я делегирую отдельно ?

### 2.6 — Verification

**Verification** — это проверка результата.

Примеры :

- прочитать diff
- запустить приложение
- открыть URL
- проверить build
- посмотреть screenshot / Artifact
- спросить ИИ : "какие инструкции ты загрузил ?"

Verification отвечает на вопрос :

> Как я узнаю, что результат можно принять ?

### 2.7 — Главная формула

> Rules дают контекст. Skills дают процедуру. Agents дают роль. Verification дает контроль.

## ЧАСТЬ 2 — Как настраивать папки и файлы в разных инструментах (18 мин)

### 3.1 — Важное предупреждение перед таблицей

Нужно сказать студентам :

> "Не нужно сегодня использовать все инструменты сразу. Вам нужно понять принцип и настроить тот инструмент, которым вы реально пользуетесь."

И еще :

> "Названия файлов меняются. Принцип остается тем же."

### 3.2 — Общая структура проекта

Для демонстрации можно показать такую папку :

```text
mon-projet/
  AGENTS.md
  CLAUDE.md
  GEMINI.md
  .agents/
    skills/
  .claude/
    skills/
    agents/
    rules/
  .gemini/
    skills/
    agents/
    commands/
  .agent/
    rules/
    skills/
```

Сразу сказать :

> "Это карта возможностей. Для новичка мы не создаем все сразу."

Минимум сегодня :

```text
mon-projet/
  AGENTS.md
  .agents/
    skills/
      spec-check/
        SKILL.md
```

Если студент работает в Claude Code :

```text
mon-projet/
  CLAUDE.md
  .claude/
    skills/
      spec-check/
        SKILL.md
    agents/
      spec-reviewer.md
```

Если студент работает в Gemini CLI :

```text
mon-projet/
  GEMINI.md
  .gemini/
    skills/
      spec-check/
        SKILL.md
    agents/
      spec-reviewer.md
```

Если студент работает в Antigravity :

```text
mon-projet/
  GEMINI.md
  AGENTS.md
  .agent/
    rules/
      project-context.md
    skills/
      spec-check/
        SKILL.md
```

### 3.3 — Codex

Для Codex главный файл проекта :

```text
AGENTS.md
```

Он нужен для :

- обзора проекта
- команд запуска
- команд проверки
- правил кода
- ограничений

В этом repo также используется структура skills :

```text
.agents/
  skills/
    gsd/
      SKILL.md
```

Педагогическая формула :

> "В Codex `AGENTS.md` — это инструкция проекта, а `.agents/skills/` — место для повторяемых процедур."

### 3.4 — Claude Code

Для Claude Code главный файл :

```text
CLAUDE.md
```

Варианты :

```text
CLAUDE.md
.claude/CLAUDE.md
~/.claude/CLAUDE.md
```

Skills :

```text
.claude/
  skills/
    spec-check/
      SKILL.md
```

Agents :

```text
.claude/
  agents/
    spec-reviewer.md
```

Правила :

```text
.claude/
  rules/
    testing.md
    frontend.md
```

Важная практическая связка :

```md
@AGENTS.md

## Claude Code
- Используй plan mode перед крупными изменениями.
```

Так Claude может читать общий `AGENTS.md`, но получать свои дополнительные инструкции.

### 3.5 — Gemini CLI

Для Gemini CLI главный файл :

```text
GEMINI.md
```

Глобальный файл :

```text
~/.gemini/GEMINI.md
```

Skills :

```text
.gemini/
  skills/
    spec-check/
      SKILL.md
```

или более универсально :

```text
.agents/
  skills/
    spec-check/
      SKILL.md
```

Команды-подсказки :

```text
.gemini/
  commands/
    review/
      spec.toml
```

Важно различить :

- `GEMINI.md` = память / правила
- `.gemini/commands` = shortcut для prompt
- `.gemini/skills` = переиспользуемая процедура
- `.gemini/agents` = специализированные агенты

Команды проверки :

```text
/memory show
/skills list
/agents list
/commands reload
```

### 3.6 — Antigravity

Для Antigravity нужно объяснить чуть иначе, потому что это agent-first IDE.

Главная идея :

> "В Antigravity агент работает не только в чате. Он планирует, действует и показывает Artifacts."

Что важно настроить :

```text
GEMINI.md
AGENTS.md
.agent/
  rules/
    project-context.md
```

Workspace rules :

```text
.agent/rules/
```

Пример :

```text
.agent/
  rules/
    env.md
    project-goals.md
    testing.md
```

Skills, если версия Antigravity их поддерживает :

```text
.agent/
  skills/
    spec-check/
      SKILL.md
```

Практическое правило для студентов :

> "В Antigravity обязательно проверяйте в интерфейсе, какие Rules активны. Не полагайтесь только на то, что файл лежит в папке."

### 3.7 — Таблица для запоминания

| Инструмент | Файл правил | Skills | Agents |
|-----------|-------------|--------|--------|
| Codex | `AGENTS.md` | `.agents/skills/<name>/SKILL.md` | Codex agents / tasks по интерфейсу |
| Claude Code | `CLAUDE.md` | `.claude/skills/<name>/SKILL.md` | `.claude/agents/<name>.md` |
| Gemini CLI | `GEMINI.md` | `.gemini/skills/<name>/SKILL.md` или `.agents/skills/...` | `.gemini/agents/<name>.md` |
| Antigravity | `GEMINI.md`, `AGENTS.md`, `.agent/rules/` | `.agent/skills/<name>/SKILL.md` если доступно | Agent Manager + Artifacts |

### 3.8 — Что сказать честно

Эти инструменты развиваются быстро.

Поэтому студент должен запомнить не только путь к папке, но и способ проверки :

- Claude Code : `/memory`, `/agents`
- Gemini CLI : `/memory show`, `/skills list`, `/agents list`
- Antigravity : Customizations / Workspace Rules / Artifacts
- Codex : спросить агента, какие инструкции и skills доступны, и проверить поведение на маленькой задаче

Ключевая фраза :

> "Настроить файл — это половина работы. Вторая половина — проверить, что инструмент его реально загрузил."

## ЧАСТЬ 3 — Демо 1 : минимальные правила проекта (18 мин)

### 4.1 — Цель демо

Не сделать идеальный файл.

Цель :

> создать короткую, полезную и проверяемую инструкцию проекта.

### 4.2 — Плохой пример

Показать плохой файл :

```md
# Rules

- Пиши хороший код.
- Будь умным.
- Делай красиво.
- Не ошибайся.
```

Спросить :

- Как проверить "хороший код" ?
- Что значит "красиво" ?
- Что ИИ должен сделать конкретно ?

Вывод :

> В vague rules нет силы.

### 4.3 — Хороший минимальный пример

Создать `AGENTS.md` или аналог для инструмента студента :

```md
# Project Instructions

## Project

This is a Next.js app for a small service business.

## Commands

- Start dev server: `npm run dev`
- Build: `npm run build`

## Rules

- Use TypeScript.
- Keep UI text in Russian.
- Do not edit `.env` files.
- Reuse existing components before creating new ones.
- Before finishing a code change, explain what was changed and how to verify it.

## Current Goal

The project must match `SPEC.md`.
```

### 4.4 — Что нужно объяснить

Каждая строка должна быть :

- конкретной
- полезной
- часто применимой
- проверяемой

Плохая строка :

```md
- Делай лучше.
```

Хорошая строка :

```md
- Do not create a new component if an existing component can be reused.
```

### 4.5 — Мини-тест

После создания файла спросить ИИ :

```text
Какие инструкции проекта ты видишь? Перечисли только те, которые относятся к этому проекту.
```

Потом дать маленькую задачу, где правило должно сработать :

```text
Добавь новый текст на страницу, но не меняй .env и не создавай новый компонент, если можно переиспользовать существующий.
```

Цель не в том, чтобы получить идеальный код.

Цель :

> увидеть, влияет ли файл правил на поведение агента.

## ЧАСТЬ 4 — Демо 2 : первый skill `spec-check` (22 мин)

### 5.1 — Почему нужен skill

Сказать :

> "Если вы просите ИИ выполнить одну и ту же процедуру больше двух раз, это кандидат на skill."

Примеры кандидатов :

- проверить spec
- подготовить commit
- провести UX review
- диагностировать ошибку
- сравнить страницу с требованиями

Для студентов самый полезный первый skill :

> `spec-check` — проверить, соответствует ли проект своей спецификации.

### 5.2 — Где создать skill

Для универсальной демонстрации :

```text
.agents/
  skills/
    spec-check/
      SKILL.md
```

Если вы показываете Claude Code :

```text
.claude/
  skills/
    spec-check/
      SKILL.md
```

Если Gemini CLI :

```text
.gemini/
  skills/
    spec-check/
      SKILL.md
```

Для Antigravity, если Agent Skills доступны в версии :

```text
.agent/
  skills/
    spec-check/
      SKILL.md
```

### 5.3 — Создать `SKILL.md`

```md
---
name: spec-check
description: Check alignment between a project spec and the existing code. Use when the user asks for a spec review, gap analysis, or peer review preparation.
---

# Spec Check

## Goal

Compare the project spec with the existing code and produce an actionable gap list.

## Procedure

1. Read the spec file first.
2. Identify the promised features and constraints.
3. Inspect only the files needed to verify those promises.
4. Classify each gap:
   - blocker
   - important
   - improvement
5. Suggest the next action for each gap.

## Output

- Summary in 3 lines maximum.
- Table: promise, current state, gap, recommended action.
- Open questions.

## Limits

- Do not edit code during the review.
- Do not invent requirements that are not in the spec.
- If the spec is too vague, explain what is missing.
```

### 5.4 — Почему этот skill подходит для начала

Он полезен, потому что он :

- конкретный
- повторяемый
- ограниченный
- не разрушает проект
- напрямую связан с личным проектом

Он не говорит :

> "Улучши мой проект."

Он говорит :

> "Сравни spec и проект, затем перечисли расхождения."

### 5.5 — Тестировать skill

Prompt для теста :

```text
Используй skill spec-check, чтобы сравнить SPEC.md с моим текущим проектом.
Не меняй файлы. Дай только приоритетные расхождения.
```

Если инструмент поддерживает автоматическую активацию, он может сам распознать skill.

Если нет, можно вызвать его явно :

```text
Используй skill spec-check.
```

### 5.6 — Что нужно наблюдать

Результат хороший, если :

- ИИ сначала читает spec
- ИИ не меняет файлы
- ИИ не предлагает 50 идей вне темы
- ИИ классифицирует расхождения
- ИИ дает следующее действие

Результат плохой, если :

- ИИ начинает кодить
- ИИ придумывает требования
- ИИ дает расплывчатую критику
- ИИ игнорирует spec

### 5.7 — Важная фраза

> "Skill не нужен, чтобы делать все. Хороший skill делает одну точную процедуру лучше и стабильнее."

---

## ЧАСТЬ 5 — Демо 3 : первый agent `spec-reviewer` (15 мин)

### 6.1 — Почему нужен агент, если у нас уже есть skill

Очень важно различить :

**Skill** :

- процедура
- переиспользуемый checklist
- загружается, когда нужен

**Agent** :

- роль
- отдельная миссия
- иногда отдельный контекст
- может быть read-only или специализированным

Простая формула :

> Skill = "как делать". Agent = "кто делает".

### 6.2 — Хороший первый агент

Для студентов лучший первый агент :

```text
spec-reviewer
```

Потому что он :

- не должен кодить
- помогает улучшить проект
- учит отделять review от implementation
- хорошо подходит для peer review

### 6.3 — Версия для Claude Code / Gemini CLI

Создать файл :

```text
.claude/agents/spec-reviewer.md
```

или :

```text
.gemini/agents/spec-reviewer.md
```

Содержимое :

```md
---
name: spec-reviewer
description: Spec review specialist. Use before coding when the project must be compared with its spec and user expectations.
---

You are a spec reviewer for a training program for non-technical founders.

Mission:
1. Read the provided spec.
2. Read only the project files needed for the review.
3. Identify contradictions, vague promises, missing features, and UX risks.
4. Do not edit files.
5. Produce a short, prioritized, actionable review.

Output format:
- Global verdict: clear / fragile / incomplete
- 3 priority problems
- 3 recommended corrections
- 1 question to ask the project owner
```

Если конкретный инструмент требует отдельного формата для `tools` или `model`, эти поля лучше добавить позже по документации инструмента. Для первого занятия важнее понятная роль и ограничение "не менять файлы".

### 6.4 — Версия для Antigravity

В Antigravity педагогически важнее всего показать миссию в Agent Manager.

Prompt для миссии :

```text
Ты мой spec-reviewer.

Прочитай `SPEC.md`, затем изучи проект без изменения файлов.
Подготовь Artifact с 4 блоками:
1. обещания spec,
2. что в проекте есть на самом деле,
3. расхождения,
4. 5 приоритетных исправлений.

Не пиши код, пока я не подтвержу Artifact.
```

Здесь ожидаемый результат — не просто текстовый ответ.

Ожидаемый результат — Artifact :

- task list
- plan
- screenshot при необходимости
- резюме проверки

### 6.5 — Версия для Codex

В Codex можно дать миссию как хорошо ограниченную задачу :

```text
Проанализируй этот проект как spec-reviewer.

Цель :
- прочитать SPEC.md
- посмотреть только нужные файлы
- не менять файлы
- найти расхождения между spec и реализацией

Формат :
- общий вердикт
- таблица расхождений
- 3 следующих действия
```

Если окружение Codex поддерживает subagents или параллельных agents, эту миссию можно делегировать agent'у review.

Но для этой сессии педагогическая идея важнее конкретного инструмента :

> У agent'а должна быть ограниченная миссия. Он не должен делать все подряд.

### 6.6 — Что нужно показать

Хороший рефлекс :

1. запустить agent в read-only режиме
2. получить его анализ
3. выбрать одну коррекцию
4. только после этого попросить ИИ реализовать

Плохая практика :

```text
Посмотри мой проект, улучши все, исправь все и задеплой.
```

Почему это плохо :

- слишком широко
- трудно проверить
- смешивает review и implementation
- дает слишком много автономии слишком рано

### 6.7 — Важная фраза

> "Agent — это не магическая кнопка. Это делегирование с ролью, лимитом и доказательством работы."

## ЧАСТЬ 6 — Verification : как проверить, что система работает (5 мин)

### 7.1 — Главный вопрос

Нужно спросить студентов :

> "Как вы узнаете, что ИИ действительно видел ваши правила, skill или agent?"

Ожидаемый ответ :

1. я проверяю, что файл лежит в правильном месте
2. я смотрю в инструменте, что он загружен
3. я прошу ИИ перечислить активные инструкции
4. я даю маленькую задачу, где правило должно изменить поведение
5. я проверяю результат

### 7.2 — Проверки по инструментам

Claude Code :

```text
/memory
/agents
```

Gemini CLI :

```text
/memory show
/skills list
/agents list
/skills reload
```

Antigravity :

- открыть Customizations
- проверить Workspace Rules
- проверить Artifacts
- дать маленькую миссию и посмотреть, соблюдает ли правила

Codex :

- проверить `AGENTS.md`
- проверить `.agents/skills/`
- спросить агента, какие инструкции проекта он видит
- дать маленькую задачу и сравнить поведение

### 7.3 — Самая важная проверка

Не верить словам.

Проверить поведением.

Пример :

Если правило говорит :

```md
- Do not edit `.env` files.
```

Нужно дать задачу, где ИИ мог бы полезть в `.env`, и увидеть, что он этого не делает.

## ДЕБРИФ + ДОМАШКА

### 5 идей, которые нужно унести с собой

1. **Prompt — это разовая просьба, а не система.**
2. **Rules дают ИИ стабильный контекст проекта.**
3. **Skill превращает повторяемую процедуру в переиспользуемый инструмент.**
4. **Agent — это специализированная роль с ограниченной миссией.**
5. **Любая AI-настройка должна быть проверена поведением, а не только наличием файла.**

### 3-2-1

- **3 вещи, которые сегодня стали понятнее**
- **2 правила, которые стоит добавить в ваш проект**
- **1 процедура, которую можно превратить в skill**

### Рекомендуемая домашка

До следующей сессии студент должен сделать 4 вещи :

1. создать или улучшить файл инструкций для своего основного инструмента :
   - `AGENTS.md`
   - или `CLAUDE.md`
   - или `GEMINI.md`
   - или `.agent/rules/project-context.md`
2. создать первый skill `spec-check`
3. подготовить один пример агента / agent mission `spec-reviewer`
4. протестировать на своем проекте :
   - попросить ИИ назвать активные инструкции
   - запустить review без изменения файлов
   - сохранить результат review

### Что сдавать

В thread сессии студент должен отправить :

1. screenshot или копию структуры папок
2. содержимое своего файла инструкций
3. содержимое `SKILL.md`
4. результат первого `spec-check` review
5. одну фразу : "что стало лучше по сравнению с обычным prompt"

### Что здесь нужно оценивать

Не :

- идеальность syntax
- количество созданных файлов
- умение пользоваться всеми инструментами сразу

А :

- студент понимает разницу между prompt, rules, skill и agent ?
- правила конкретные и проверяемые ?
- skill делает одну процедуру, а не все подряд ?
- agent имеет ограниченную роль ?
- студент проверил, что ИИ реально использовал инструкции ?
